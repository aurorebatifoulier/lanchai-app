# LANCHAI — pre-beta audit (November 2026)

**Date:** 3 November 2026 · **Code audited:** `master` at `047da1d` · **Scope:** app, Cloud Functions,
Firestore and Storage rules, config.
**Method:** read-only. Four parallel reviews (security, stability, performance & cost, clean-up)
read the code file by file. The critical and high findings were then re-checked by hand in the code.
No code was changed.

Severity: **critical** = must fix before any tester touches it · **high** = fix before the closed
beta · **medium** = fix during the beta · **low** = backlog. Effort: **S** < 2 h · **M** half a day
to a day · **L** several days.

---

## 0. Verdict

**The app is viable for a closed beta of 20–30 trusted testers in Vientiane**, once the ~10
**high** items below are fixed. Those fixes are small, about 2–3 days of work in total.

- **What holds up well:**
  - **Server-side money logic.** Every amount — tier price, exchange rate, per-unit deposit,
    coupon %, promo discount — is recomputed inside a transaction, with stock serialised per
    product. Renters cannot set prices, points, tiers, statuses or roles.
  - **Rules.** Strict field allow-lists, consistent admin checks.
  - **Secrets.** None in the repo.
  - **Defensive code.** Most of the code is already defensive.
- **What would hurt real testers:**
  - Booking times follow the phone's timezone instead of Vientiane time.
  - Bag checkout deletes items it didn't book.
  - The chat can silently fail to reach staff.
  - A slow network can create duplicate orders.
- **Security:**
  - Renters can delete their own ID copies directly in Storage (bypassing the retention rules).
  - The free booking flow can be used to lock all stock.
- **Performance:** most of the "laggy" feel is Expo Go dev mode. The one real issue is two
  endless JS-thread animations (Account header, Home "Rent. Return. Repeat.").
- **Firestore cost:** not a concern. About **$0/month at 50 users**, about **$5–6/month at 500**.
  A few queries are unbounded and should get a limit before the public launch.

**Before a public launch** (on top of the above): App Check, booking-abuse limits, the medium
security items, crash reporting, a restricted API key and budget alerts, a lawyer review of the
legal texts (already tracked), and a staging Firebase project.

### Checked and fine

- **Secrets:**
  - `.env.local` holds only the public `EXPO_PUBLIC_FIREBASE_*` config. It is gitignored and was never committed (history searched for Brevo keys, `AIza…`, private keys and service accounts).
  - The Brevo key is a Functions secret, never in the app bundle.
  - The Firebase web config is public by design. **Restrict the API key** in Google Cloud Console (Android package + SHA-1, iOS bundle id, allowed APIs only).
- **Personal data:**
  - ID and residency files are stored as **paths** (no download URLs), with owner/admin read only.
  - Agreements are emailed as attachments.
  - Function logs use uids and email hashes; the reset link is never logged.
  - All email HTML is escaped.
- **Server-only data and rules:**
  - Admin collection: not client-writable, not listable.
  - Every admin callable checks `admins/{uid}`; every renter callable uses `accountUid` (guests refused).
  - Users allow-lists cover loyalty, coupons, `customerType`, BtoB status, ID and residency fields.
  - Renter cancellation is pinned to status, timestamp and source.
  - Reviews are validated, one per returned reservation, with the rating recomputed on the server.
  - These are server-written only: promo codes, grants, identity checks, residency requests, agreements, booking holds, product locks, referrals, invite codes, deletion log, loyalty history, occupancy.
  - Promo and coupon restores are idempotent.
  - The hosting redirect page has a strict path allow-list, so there is no open redirect.

### What App Check would add

It proves a request comes from your real app (Play Integrity on Android, App Attest on iOS) before
Firestore, Storage, Functions or Auth accept it. That shuts down scripted use of the public API key,
which is what makes S-H2, S-M2, S-M4, S-M5 and mass anonymous accounts cheap today.

It does **not** fix rule-logic bugs (S-H1, S-M1, S-M3) or stop a real user on a real phone.

It needs a dev or EAS build (Expo Go can't attest; use debug tokens). Run it in **monitor** mode
first, then enforce.

### The 10 most likely beta bugs (step by step)

1. **Tourist books from abroad.** Phone on CET, picks "10:00" → stored and shown as 16:00
   Vientiane; "15:00" is refused as outside opening hours (T-H1).
2. **Bag with one undated item.** Continue → Confirm → two items booked, the third silently
   deleted (T-H2).
3. **First chat on a weak connection.** No conversation document → "Could not send" → retries
   create duplicates → staff never see the thread (T-H3).
4. **Slow 3G at Confirm.** The server books, the client times out → "Could not confirm" → second
   tap → a second order and a second confirmation email (T-H4).
5. **Old bag.** Last week's dates → checkout fails "too soon" without naming the item (T-M1).
6. **First launch without data.** The anonymous sign-in fails → login wall until restart (T-M2).
7. **Checkout on a weak signal.** Exchange rate not loaded → "No items to check out." (T-M6).
8. **Late return across several orders.** One failing update aborts `lateReturnAlerts` → late-fee
   emails lost for the orders already flagged (T-M3).
9. **Book then cancel quickly.** Out-of-order triggers → product shown as booked to everyone (T-M4).
10. **Busy 18:00 reminders / slow Brevo.** Job timeout → reminders never sent (T-M5).

Runners-up: a forced sign-out while chat is open crashes (T-L2); double loyalty credit (S-M6).

## 3. Performance and cost

### Dev mode vs real issues — test production-like on the S25

Expo Go dev mode is unminified, runs `__DEV__` checks, LogBox and DevTools hooks, and is 2–5× slower
for lists and animations. Expo Go also compiles JS on the device at start, so **cold start in Expo Go
is never representative**.

1. **Production JS in Expo Go (5 min, no build):**
   `npx expo start --no-dev --minify --clear`, then open the project in Expo Go.
   - Scrolling and animation smoothness are now representative.
   - Dev menu → "Performance monitor" shows JS vs UI FPS: a JS FPS drop while idle on Account
     confirms P-1.
2. **Real release-like APK (the true measurement):** `eas build -p android --profile preview`
   (`eas.json` already has a `preview` profile building an APK), then install it on the S25.
   Before building:
   - The `EXPO_PUBLIC_FIREBASE_*` values live only in `.env.local`, which is gitignored, so EAS
     won't see them. Create them as EAS environment variables (`eas env:create --environment
     preview …`), or the build starts with an empty Firebase config.
   - Google sign-in needs the EAS keystore SHA-1 in Firebase, plus `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`.
